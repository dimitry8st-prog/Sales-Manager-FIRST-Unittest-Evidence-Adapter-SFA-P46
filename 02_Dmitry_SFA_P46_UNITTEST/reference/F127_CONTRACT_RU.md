'# F1-27 R1 — полный русский текст замороженного интерфейса

Проект `sales-manager-first`. Функция `summarize_release_evidence(plan:dict, records:list[dict])->dict`, исходный путь `source/sales_release_evidence.py`. Python 3.10+ и стандартная библиотека. Чистая функция: нет ввода-вывода, сети, переменных окружения, часов, дочерних процессов, сохранения входов глобально и мутаций. Это сводка локальных регрессионных доказательств FG12, а не разрешение релиза.

## Вход

Каждый объект имеет точный набор ключей. Встроенные типы `dict/list/str/int/bool` проверяются точным типом; подклассы запрещены. Тип `int` не принимает `bool`. Идентификаторы релиза, набора и случая соответствуют полному ASCII-шаблону `[A-Za-z0-9_.-]{1,128}`.

План имеет ровно поля `schema_version,release_id,suites`. Версия — `FIRST_RELEASE_TEST_PLAN_V1`; `release_id` — корректный идентификатор; `suites` — непустой список. Набор имеет ровно `suite_id,required_cases,optional_cases`; `suite_id` уникален; оба списка содержат идентификаторы случаев. Идентификаторы случаев уникальны внутри набора между обоими списками, но могут повторяться в разных наборах. Во всём плане должен быть хотя бы один обязательный случай; набор без обязательных случаев допустим.

Аргумент `records` — список, в том числе пустой. Запись имеет ровно `release_id,suite_id,case_id,attempt,status,exit_code,skip_count`. Релиз совпадает с планом, набор и случай существуют в плане. Поле `attempt` — точный `int>=1`; `status` — `PASS/FAIL/ERROR/SKIP`; `exit_code` — любой точный `int`; `skip_count` — точный `int>=0`. Для `PASS` обязательны `exit_code=0,skip_count=0`; для `FAIL/ERROR` — `exit_code!=0,skip_count=0`; для `SKIP` — `exit_code=0,skip_count>=1`. Чужие или неизвестные идентификаторы делают весь список записей недействительным, не игнорируются.

## Проверка и диагностика

Сначала проверить весь план, затем все записи по порядку, включая вытесненные попытки. Только первая ошибка; частичная сводка не возвращается. Сначала проверить тип контейнера, затем точные ключи: коды `INVALID_TYPE/INVALID_KEYS` указывают путь контейнера. Порядок полей плана: `schema_version,release_id,suites`; в наборе — `suite_id,required_cases,optional_cases`; элементы списков — по порядку. Повтор идентификатора даёт `DUPLICATE_ID` по пути повторного идентификатора. Пустой список наборов или отсутствие обязательного случая во всём плане дают `INVALID_VALUE` по пути `plan.suites`; глобальная проверка выполняется после всех наборов.

Поля записи проверяются в порядке `release_id,suite_id,case_id,attempt,status,exit_code,skip_count`. Ошибка типа даёт `INVALID_TYPE`; ошибка формата, диапазона или перечисления — `INVALID_VALUE`; неизвестный идентификатор после проверки формата — `UNKNOWN_ID` по соответствующему полю. Несовместимость статуса, кода завершения и пропусков даёт `INVALID_VALUE` по пути `records[i].status` после проверки всех полей. После проверки записи сравнить ключ `(suite_id,case_id,attempt)` с предыдущими: точный повтор одинакового словаря удаляется; разные значения дают `CONFLICT` по пути `records[i]`. Конфликт старой вытесненной попытки тоже делает весь ввод недействительным. Форматы путей: `plan`, `plan.suites`, `plan.suites[i].suite_id`, `plan.suites[i].required_cases[j]`, `records`, `records[i]`, `records[i].attempt` и аналогичные.

## Детерминированная сводка

Выход имеет ровно `schema_version,release_id,status,suites,counts,errors,external_effect_authorized,gate_acceptance`. Версия всегда `FIRST_RELEASE_EVIDENCE_V1`; оба флага всегда встроенный `False`. Валидный `release_id` копируется. При недействительном плане он копируется только из точного `dict` с валидным встроенным строковым идентификатором, иначе возвращается `null`.

Поле `status` равно `REQUIRED_COMPLETE` только если последние результаты всех обязательных случаев имеют статус `PASS`; иначе — `BLOCKED`. Провалы, пропуски и отсутствие результатов необязательных случаев не блокируют. Набор применяет то же правило; набор без обязательных случаев имеет `REQUIRED_COMPLETE`. Список `suites` сохраняет порядок плана; набор имеет ровно `suite_id,status,cases,counts`. Случаи в `cases` следуют сначала в порядке `required_cases`, затем `optional_cases`. Случай имеет ровно `case_id,required,status,attempt,exit_code,skip_count`. Поле `required` имеет тип `bool`; `status` — последний статус либо `NOT_RUN`. Отсутствующий результат имеет `attempt:null,exit_code:null,skip_count:0`. Выбирается наибольший `attempt` отдельно для каждой пары набора и случая; порядок записей не влияет. Последний `SKIP` обязательного случая не проходит проверку.

Поле `counts` имеет ровно `required_total,required_pass,optional_total,optional_pass,not_run,fail,error,skip`; все значения — встроенные неотрицательные целые. Поля итогового количества считают плановые случаи, а поля количества успешных — последние `PASS` соответствующего типа. Поля `not_run/fail/error/skip` считают последние статусы всех случаев, а не попытки и не сумму `skip_count`. Счётчики наборов локальны; верхние счётчики являются суммами по наборам. На валидном входе `errors=[]`.

Недействительный результат имеет статус `INVALID_PLAN/INVALID_RECORDS`, `suites=[]`, восемь нулевых счётчиков и ровно `errors=[{code,path}]`. Идентификатор релиза и флаги определяются правилами выше. Некорректный ввод не вызывает исключения. Неожиданные ошибки реализации и среды исполнения не поглощаются.

Входные записи — доказательства, нормализованные **по каждому тестовому случаю** доверенным интеграционным адаптером, а не сырые агрегаты исполнителя тестов. Записи `FAIL/ERROR` с `skip_count>0` намеренно невалидны: адаптер должен разделить и нормализовать отдельные результаты до вызова F1-27. Сам F1-27 не реализует адаптер и не разрешает релиз.
